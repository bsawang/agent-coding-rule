# 难 bug 的诊断

复杂的 bug 与性能回退按六个阶段走。跳过阶段必须在明确说明理由之后。

**先脱敏** —— 要展示命令、输出、抓取的产物时，密钥一律写成 `<REDACTED>`；循环靠环境变量驱动，凭据留在环境里而不出现在你展示的内容中。抓来的产物带鉴权头，只引用有信号的那几行。脱敏后信息不够诊断，就直说，然后问用户。

## 阶段一：造一个反馈回路

**这一步就是全部。** 有了针对**这个** bug 会变红的紧回路，原因一定能找到 —— 二分、验证假设、插桩都只是消费它。没有它，盯着代码看多久都没用。

花不合比例的时间在这一步。**要凶一点，要有创意，不许放弃。**

构造手段，大致按这个顺序试：

1. **失败测试** —— 任一层 seam：单元、集成、端到端。
2. **curl / HTTP 脚本** —— 打运行中的 dev server。
3. **CLI 调用** —— 带固定输入，stdout 与已知正确的快照对比。
4. **无头浏览器脚本** —— 驱动界面，断言 DOM / console / network。
5. **重放抓到的轨迹** —— 把真实的网络请求 / payload / 事件日志存盘，隔离地重放一遍。
6. **一次性夹具** —— 起系统的最小子集（一个服务、mock 掉依赖），一次函数调用就能走到出 bug 的代码路径。
7. **属性 / 模糊测试** —— bug 是「有时候输出不对」时，跑 1000 个随机输入找失败模式。
8. **二分夹具** —— bug 出现在两个已知状态之间时，把「在状态 X 启动、检查、重复」自动化，好让 `git bisect run` 用。
9. **差分回路** —— 同一输入跑旧版与新版（或两套配置），对比输出。

**把回路当产品来打磨**：能不能更快（缓存 setup、跳过无关初始化、缩小测试范围）？信号能不能更锐（断言具体症状，而不是「没崩」）？能不能更确定（固定时间、固定随机种子、隔离文件系统、冻结网络）？30 秒且飘的回路比没有好不了多少；2 秒且确定的回路是调试超能力。

**不确定的 bug**：目标不是干净的复现，而是**更高的复现率**。把触发循环 100 次、并行化、加压力、收窄时间窗、注入 sleep。50% 的飘 bug 可以调，1% 的不行 —— 把复现率抬到能调为止。

**实在造不出回路**：停下来说明，列出试过什么，向用户要 (a) 能复现的环境，(b) 脱敏后的产物（HAR、日志、core dump、带时间戳的录屏），或 (c) 加临时生产插桩的许可。**没有回路就不要进入假设阶段。**

**完成判据** —— 回路**紧**且**能变红**：你能说出**一条命令**，已经**至少跑过一次**（展示调用与输出，脱敏后），并且它 ① 走的是真正出 bug 的代码路径、断言的是**用户描述的那个症状**（不是「跑起来没报错」，而是能逮住这个 bug）；② 每次跑结论一致；③ 几秒级，不是几分钟；④ 可以无人值守跑。

> 在命令存在之前就去读代码编理论 —— 那正是这套流程要拦住的失败。没有能变红的命令，不进入阶段二。

## 阶段二：复现 + 最小化

跑回路，看它变红。确认：失败模式是**用户**描述的那个（不是恰好挨着的另一个 —— 错的 bug 会导致错的修复）；多次运行都复现（不确定的 bug 达到足够复现率）；症状被完整记录（报错信息、错误输出、慢的耗时），后面阶段要靠它验证修复。

**最小化**：红了之后，把它缩到**仍然会红的最小场景**。输入、调用方、配置、数据、步骤**一次砍一个**，每砍一次重跑回路，只留对失败有支撑的部分。做完的标准是**剩下每个元素都是承重的** —— 去掉任一个，回路就变绿。

复现**且**最小化之后，才往下走。

## 阶段三：假设

先一次性生成 **3–5 条排好序的假设**，再动手验。只生成一条会被第一个看似合理的想法锚住。

每条假设必须**可证伪**，写出它预测什么：「如果 X 是原因，那么改 Y 会让 bug 消失 / 改 Z 会让它更严重。」写不出预测的假设是感觉，丢掉或者磨尖。

**把排序后的假设列表给用户看** —— 他们常有领域知识能瞬间重排（「我们刚上线了一个改动，正好是第 3 条」）。

## 阶段四：插桩

每个探针必须对应阶段三的某条预测。**一次只改一个变量。**

工具优先级：① 调试器 / REPL 单点查看（一个断点胜过十行日志）；② 在能区分假设的边界上打定向日志；③ 不要「全打日志然后 grep」。

**每条调试日志带唯一前缀**（如 `[DEBUG-a4f2]`），收尾时一次 grep 就能清干净。没前缀的日志会活下来。

**性能回退走另一条**：先建立基线测量（计时夹具、profiler、查询计划），再二分。先测量，后下手。

## 阶段五：修复 + 回归测试

**先写回归测试，再修** —— 但仅当存在**正确的 seam**。

正确的 seam 是能让测试复现**真实 bug 形态**（即在调用点发生的样子）的那个。手上只有太浅的 seam（bug 需要多个调用方，却只能写单调用方测试；复现不了触发链的单元测试），在那里写回归测试只会给出虚假的信心。

**没有正确的 seam，这件事本身就是发现** —— 记下来：代码结构正在阻止这个 bug 被钉死。这条要反馈给下一阶段。

有正确 seam 时：把最小复现变成一个失败的测试 → 看它失败 → 应用修复 → 看它通过 → 用阶段一的回路跑一遍**没最小化过**的原始场景。

## 阶段六：清理

宣布完成之前必须：

- [ ] 原始复现不再复现（重跑阶段一的回路）
- [ ] 回归测试通过（或「没有合适 seam」这件事已被记录）
- [ ] 所有 `[DEBUG-...]` 插桩已删除（grep 前缀确认）
- [ ] 一次性原型已删除或移到明确标记的调试位置
- [ ] 正确的假设写进了 commit / PR 信息，让下一个调试的人受益
