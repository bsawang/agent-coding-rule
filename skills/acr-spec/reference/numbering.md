# 编号规范：模块 Mx + 子需求 Mx.y

**归属**：acr-spec 的 reference，brainstorm 和 spec 都引用这里。

## 体系

两层编号，**全文唯一**，贯穿 prd → spec → progress → cycle → 快道调整日志。

```
M1 短链生成             ← 模块：业务价值单元（prd 切分）
  M1.1 创建短链          ← 子需求：独立可验的最小单元
  M1.2 短码生成算法
M2 短链跳转
  M2.1 正常跳转
```

## 规则

| 规则 | 说明 |
|---|---|
| 模块编号**锁定后不改** | 项目启动时一次性分配完所有 Mx。新增追加 Mn+1，废弃加 🗑，**永不重排** |
| 子需求编号**锁定后不改** | 新增追加 Mx.y+1，废弃加 🗑，**永不重排**，合并保留小编号大的标废弃 |
| 编号 = ID，**不暗示顺序** | 依赖关系用**需求树（mermaid flowchart）**画箭头表达 |
| 跨模块依赖**允许** | M2.1 依赖 M1.2 + M1.4，直接在需求树里画箭头 |
| 引用格式标准化 | 所有文档引用子需求时用 `[M1.2](./spec.md#m12)`（`#` 锚点 = `#` + 小写 M + 无点数字） |

## 谁负责编

| 层级 | 谁分配 | 在哪分配 | 规则 |
|---|---|---|---|
| 模块 Mx | brainstorm | prd.md §2 | 业务价值单元，一个模块 = 用户能单独感知的功能域 |
| 子需求 Mx.y | spec | spec.md §4 | 技术实现单元，一个子需求 = 能独立写验收 + 详细设计 + 跑测试 |

**brainstorm 只切 Mx，不管 Mx.y**。Mx.y 是 spec 的事——brainstorm 没写，spec 有权加，但必须归属 brainstorm 定义过的 Mx（MX 集合对账硬检查）。

## 废弃怎么处理

| 场景 | 做法 |
|---|---|
| 整个模块废弃 | prd.md 改标题加 🗑，spec.md 改标题加 🗑，spec 保留 Mx.y 不动 |
| 某个子需求废弃 | spec.md 改标题加 🗑，PROGRESS.md 里标 ⬜ + 备注废弃原因 |
| 合并两个子需求 | 保留小编号（如 M1.2），大编号（如 M1.3）标 🗑，内容合并进小编号 |

**不删除、不重排**。编号是永久引用，半年后能精确定位。
