# 开发循环

## 入口：三档判定

档位由**改动落在哪一层文档**决定，不由「改动大小」决定 —— 可判、单调、只能往上升。

本节是**分档的唯一真相源**（`~/.claude/CLAUDE.md` 的「快速通道」一条指向此处，不重述）。

```
快道     spec 不变                样式布局 · 实现细节微调
         └ 记一条调整日志即完，免设计评审、免循环；分主题提交纪律不变

标准档   spec 变，概要设计不变     在既有模块职责内增改功能点
         └ spec 修订 + 详细设计 + 走完整循环

完整档   概要设计 或 架构设计 变    新增模块 · 模块边界变 · 技术底座变
         └ spec → 概要 → 架构 → 详细 + 走完整循环
```

**判定句（自检两问）**：

> ① 这次改动，spec 里那句需求描述要改吗？要改 → 不是快道。
> ② 模块划分要改吗？要改 → 完整档。

**升级规则**：任何一档进行中发现上层文档要改，**就地升级、不硬推** —— 快道中 spec 要改 → 升标准档；标准档中结构要变 → 升完整档。

## 一个完整循环（标准档 / 完整档）

```
④ 设计评审 ★  用户确认门槛
⑤ 进度追加 ★  在 PROGRESS.md 建本次循环
⑥ 实施        按功能点循环
⑦ 测试        全量验证 + 证据留存
⑧ 文档回溯 ★  偏离回填 · 进度收尾 · 验收标准勾对
⑨ 收尾        分主题提交 → 集成决策 → 推送
```

### ④ 设计评审

把方案复述成 3–5 行（含**假设**与**边界**），等用户明确确认。

硬规则「设计未经用户确认，不写任何实现代码」在 `~/.claude/CLAUDE.md`（全局常驻，不在本 skill 重述）。本步做的是**拦截**：

- **Edit / Write 改实现代码一律拦下**，直到用户明确确认。
- 探索性读取、跑命令、写 spec / 文档 / 工单不在拦截范围。
- 用户要求修改 → 退回设计阶段（`acr-brainstorm` / `acr-spec` / `acr-design-docs`）。

**完成判据**：用户明确确认，且确认范围（哪一版方案、确认了哪些假设与边界）有记录。

### ⑤ 进度追加

按 `acr-progress` 在 `PROGRESS.md` 建本次循环：关联 spec 组 + 功能点清单 + 验收标准。

**完成判据**：每个功能点都能在 spec 里找到对应的可判验收标准。找不到 → 退回 `acr-spec` 补。

### ⑥ 实施：功能点循环

一次只推进一个功能点：

```
1 定标准   从 spec 拿验收标准；不可判 → 打回 spec 重写
2 定接口   这个点对外暴露什么 / 依赖什么 / 边界在哪
3 失败测试 先让它红
4 最小实现 只做到让它绿
5 全量验证 不是只跑本点
6 自检+证据 命令 + 原始输出
7 收点     标记完成 → 下一点
```

三条规矩：**一次一个功能点**；**不攒到最后一起验证**；**每点完成必带证据**。

具体做法见 [reference/tdd.md](reference/tdd.md)（红绿循环、测试放哪、反模式）。

**完成判据**：每个功能点都有本轮的新鲜证据，且本阶段**零未授权 git 动作**。

### ⑦ 测试

任何成功声明（「完成 / 通过 / 修好 / 已解决」）之前，必须有**本轮消息内**跑过的新鲜验证证据。拿不出 → 撤回声明。

> 没在本消息里跑过验证命令，就不许声称通过。

| 借口 | 现实 |
|---|---|
| 「应该能过了」 | 去跑 |
| 「我很确定」 | 确定 ≠ 证据 |
| 「lint 过了」 | lint ≠ 编译 |
| 「只是这一次」 | 没有例外 |

**重构变体**：证据是**行为不变证明** —— 基准全绿，且是同一份基准。

**端到端跑通 / 浏览器级验收**走全局 `verification` 与 `webapp-testing`；本步只管**证据门槛**（本消息内跑过、输出在场）。

**完成判据**：全量验证通过，且输出留在本轮对话里。不过关就不进 ⑧ —— 硬规则「测试不通过不进入收尾」见 `~/.claude/CLAUDE.md`。

### ⑧ 文档回溯

三件事，缺一不可：

1. **偏离回填** —— 实现偏离设计的地方，明确选**改设计文档**还是**改代码**。只有这两个出口，不允许「先这样吧」。
2. **进度收尾** —— 按 `acr-progress` 更新状态与证据。
3. **验收标准勾对** —— spec 里每条 F 的验收标准逐条确认。

另外重跑一遍结构秩序检查（`acr-design-docs` 的七条）—— 文档在循环中被改过，正是顺序最容易乱掉的时刻。

**完成判据**：每条偏离都有出口，每条验收标准都有结论。

### ⑨ 收尾

按序执行：

| 步 | 动作 |
|---|---|
| 0 | **评审意见核实** —— 完整读完 → 复述技术要求 → 对照代码核实 → 技术上站得住才实现。禁止「你说得对！」这类附和；任一条不清楚就**全部停下先问**，不许先做清楚的几条 |
| 1 | **文档同步** —— 按仓库文档地图更新。**README 只同步用户侧内容**（什么变了会影响用它的人），开发内容一律进 `docs/`，分工见 `acr-design-docs`；进度表、调整日志按各自 skill |
| 2 | **分主题提交** —— `feat` / `fix` / `docs` 分开，一主题一提交 |
| 3 | **集成决策** —— 直接合 / 开 PR / 保留分支，**给选项让用户选** |
| 4 | **推送** —— 按用户的 git 词执行精确动作序列 |

代码评审的做法见 [reference/review.md](reference/review.md)。

## 边界

- **不自发 git** —— 按个人记忆「开发中不自发 git」执行（真相源在那里，本 skill 不重述）；只读查看（`status` / `diff` / `log`）不受限。
- **假设塌方就停** —— 撞见下列任一，停止写码、退回设计阶段：需修改已确认的接口才能继续 / 出现方案没覆盖的边界 / 同一处反复打补丁 / 实现与 spec 描述的不是一回事。
- 不修 bug 之外的东西（诊断见 [reference/diagnosing.md](reference/diagnosing.md)）。
- 不写需求与设计文档（→ `acr-spec` / `acr-design-docs`）。
- 快道改动不进本流程（→ 直接记 `acr-spec` 第 9 节的调整日志）。
- **从零脚手架新项目**走全局 `create-project`；本流程管既有项目的改造与新增。
