# 设计模块接口时的词汇

设计「分几块」「接口怎么定」「seam 放哪」时用这套词。用词一致本身就是价值 —— 不要换成「组件」「服务」「API」「边界」这些近义词。

## 词表

**模块** —— 任何有接口有实现的东西。尺度无关：一个函数、一个类、一个包、一条贯穿多层的切片都算。别叫它「单元」「组件」「服务」。

**接口** —— 调用方正确使用这个模块所必须知道的一切：类型签名，以及不变量、调用顺序约束、错误模式、需要的配置、性能特征。别缩写成「API」「签名」—— 那两个只覆盖类型层面。

**实现** —— 模块内部的代码。与**适配器**区分：小适配器可以有大实现（Postgres 仓库），大适配器可以有小实现（内存假件）。讨论 seam 时用「适配器」，其余用「实现」。

**深度** —— 接口上的杠杆：调用方（或测试）每学一单位接口能撬动多少行为。实现量大而接口小 = **深**；接口和实现差不多复杂 = **浅**。

**seam** —— 不修改该处就能改变行为的位置；也就是模块接口所在的那个**位置**。seam 放哪是独立的设计决定，和「后面放什么」是两件事。别用「边界」—— 那个词被领域驱动设计占用了。

**适配器** —— 在某个 seam 上满足某个接口的具体东西。描述的是**角色**（填哪个槽），不是内容（里面是什么）。

**杠杆** —— 深度给调用方的好处：每学一单位接口多得一分能力。一份实现，在 N 个调用点和 M 个测试上回本。

**局部性** —— 深度给维护者的好处：改动、bug、知识、验证都集中在一处，而不是散到各个调用方。改一次，处处都改好了。

## 深与浅

深模块 = 小接口 + 大实现；浅模块 = 大接口 + 小实现（要避免）。

设计接口时三问：方法能不能再少？参数能不能再简单？还能不能再藏点复杂度进去？

## 四条判据

- **深度是接口的属性，不是实现的属性**。一个深模块内部完全可以由小的、可替换的零件组成 —— 它们只是不属于接口。模块可以有**内部 seam**（实现私有，给自己的测试用），也可以有接口处的**外部 seam**。
- **删除测试**：想象删掉这个模块。复杂度消失了 → 它是个传声筒；复杂度在 N 个调用方那里重新冒出来 → 它挣到了自己的位置。
- **接口即测试面**：调用方和测试走的是同一个 seam。想绕过接口去测，多半说明模块形状不对。
- **一个适配器 = 假 seam，两个适配器 = 真 seam**。没有东西真的在 seam 两侧变化，就别引入这个 seam。

## 为可测性设计

1. **依赖靠传入，不靠内部创建** —— `processOrder(order, gateway)` 而不是在函数里 `new Gateway()`。
2. **返回结果，不产生副作用** —— `calculateDiscount(cart): Discount` 而不是直接改 `cart.total`。
3. **接口面要小** —— 方法少，测试就少；参数少，setup 就简单。
