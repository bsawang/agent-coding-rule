# 存量项目文档重整

**输入**：一个已有项目的既有文档（可能散乱、结构不一、缺章节）。
**输出**：`docs-rebuilt/` 里的重整稿 + `GAPS.md` 缺陷文档。

**定位**：逆向，即**把原项目文档重新整理**成标准结构。代码只作**交叉参照** —— 用来验证文档里的说法是否属实，不是内容来源。

## 三条硬规矩

| 规矩 | 为什么 |
|---|---|
| **新建文件夹，原文档一律不动** | 重整的是用户既有文档。原 `docs/` 原样保留，比对满意后由用户自行决定是否替换 —— 本项目不动手替换 |
| **只搬不删** | 不做内容删减。冗余合并、说法冲突的处置交用户裁决，不擅自选一个 |
| **不能证实的内容不进正文** | 含糊、矛盾、代码里找不到依据的内容进 `GAPS.md`，不进正文 |

## 流程

```
① 摸底        原文档清单（形式 / 章节 / 完整度）+ 代码结构作交叉参照
② 定范围 ★    按域增量，不全量 —— 常改的域先重整，不动的不碰
③ 映射        建「旧章节 → 新模板章节」映射表
④ 重整        按结构秩序写入新文件夹
⑤ 评审 ★      逐份与用户过 → 产出 GAPS.md
⑥ 回填        用户按 GAPS 补充 → 并入新文档 → 条目状态更新
```

★ = 硬检查点，不许跳过 —— ② 与 ⑤ 都要用户过目才往下走。

**① 摸底固定清单**（防漏）：原文档清单 · 目录树 · 入口 · 数据模型 · 依赖 · 配置。后四项兼作交叉参照 —— 入口和数据模型最容易漏，也最能证伪文档里的说法。

**② 定范围 ★ 按域增量**：常改的域优先。全量补齐一个老项目是数小时的活，而不常动的域建了文档也没人看。

**这一关要用户过目才算数**：有多个域时，列出候选让用户挑。**只有一个域时也必须明说** ——
「这个项目只有一个域，全量重整等价于按域增量」—— 然后才动手。**不许静默跳过**：
你判断「没得选」这件事本身要让用户看到，因为你的判断可能错。
（实测踩过：一次重整里 ① 摸底直接跳到 ④ 重整，全程没提范围，用户无从知道你判过还是漏了。）

**③ 映射表**：一行一个旧章节 → 新章节。映射不上的内容**不许丢**，先挂到 `GAPS.md` 里「无归属」一类。

**④ 重整**：结构按 `acr-design-docs` 的三层模板与七条结构秩序（同样是 `<slug>.hld.md` / `ARCHITECTURE.md` / `<slug>.lld.md` 那套，不另造格式）。每搬一条，在映射表上勾一条 —— 这就是防丢的机制。

**映射表放哪**：写进 `GAPS.md` 的附录 —— 它和缺陷清单同属评审产物，放一起便于对照。

**正文里标出存疑处**：「不能证实的内容不进正文」不等于装作没看见。做法是两步分写：

- **正文结论只写能证实的那一个**（代码或原文档明确支持的）
- **原文档里与此不符 / 缺失的说法，就地用一条 ⚠️ 说明并挂 GAPS 编号**

这样「不进正文」这件事**可核对** —— 读者拿到正文结论，也知道争议在哪、该去哪补。

> 实测的好样子：正文写「存储是单文件 JSON，`data/meta.json`」（有代码依据），紧跟一条
> 「⚠️ 原 `design.md` 称用 SQLite、原 `README` 称 v2 打算改 SQLite，均与实现不符 —— 见 GAPS #3」。
> 结论是确的、争议是显式的、一条都没编。

**⑤ 评审**：不产出「批准 / 驳回」，产出**缺陷文档**（[reference/gaps-template.md](reference/gaps-template.md)）。逐份与用户过一遍，把该补的、说不清的、自相矛盾的、代码里证不了的，都记成条目。

**⑥ 回填**：用户补一条、勾一条。补完的内容并进重整稿。

## 产出结构

```
<项目>/
  docs/                 ← 原文档，原样不动
  docs-rebuilt/         ← 重整产出（新建文件夹）
    ARCHITECTURE.md
    PROGRESS.md
    specs/<domain>/*.spec.md · *.hld.md · *.lld.md · *.discussion.md
    GAPS.md             ← 缺陷文档
```

## 边界

- **不替换原文档** —— 产出即交付，替换与否由用户自己决定。
- 不写新需求（→ `acr-cycle`）、不写新 spec（→ `acr-spec`）。
- 不因为「文档看起来不对」就改代码 —— 代码里的现象记进 `GAPS.md`，由用户裁决是文档错还是代码错。
