# 无状态执行

**定位**：工具层，无状态。上下文全来自 PROGRESS.md，cycle 不存任何内部状态。

**前置**：progress 已接收 plan 的下发声明 + 计划侧对账已过 + PROGRESS.md 已写好。cycle 入口 = progress 把 PROGRESS.md 交给 cycle。

## 执行：子需求循环

一次一个子需求，按依赖序（progress 里锁好的拓扑序）逐个执行。

```
对每个 Mx.y（progress 里的依赖序）：

  ① 读 spec —— 拿验收标准 + 详细设计（接口 / 边界 / 错误处理）
              验收不可判 → 打回 spec 重写

  ② TDD RED-GREEN —— **写测试 → 真跑确认红 → 写最小实现让它绿 → 贴红+绿输出**
     RED 是硬约束（必须真看到 FAIL，见下）
     GREEN 就是让刚才那个测试过 —— 不许多写一行投机代码

  ③ 影响分析（可选）—— 列出本改动可能影响的外部功能 + 可选测试计划（不真跑）
     例："改了 note.create slug 逻辑 → 可能影响 M2.1 标签筛选依赖 slug / 可选跑 pytest tests/test_tags.py"
     → 追加到 PROGRESS.md 本子需求证据列后面，不算 F1 证据，仅作参考
     → 没影响或懒得写 → 跳过，不卡 ✅

  ④ 收点 ✅ —— 贴证据（命令 + 输出 + 轮次）→ 原子标记完成 → 触发 F1
              没有本轮新鲜证据不许写 ✅
```

**四条规矩**：**一次一个子需求**；**不攒到最后一起验证**；**每点完成必带证据**；**收点是原子的**。

### 第 ② 步：RED 必须真看到失败（硬约束）

不是"应该写失败测试"，是**必须看到失败才能继续**。流程：

1. **写测试** —— 按 spec 验收标准写一条最小测试（垂直切片，一次一个 seam）
2. **执行测试** —— 必须真跑一遍（`pytest -v tests/test_x.py::test_y` 或等价命令）
3. **确认红** —— 测试输出必须显示 FAIL / ERROR / assertion failed，**不是 passing**
4. **记录** —— 把**红的输出片段**（`FAILED tests/test_x.py::test_y - AssertionError...`）贴进 PROGRESS.md 本子需求的证据列（F1 对账需要 RED 片段作为 TDD 合规证明）

**违反即停**：如果测试一上来就是绿的（因为前一个子需求顺带实现了），不能静默跳过。必须：
1. **显式声明** —— 说清为什么前一个子需求让它绿了
2. **反向验证** —— 现场把实现改坏（注释掉 / 改个值），确认测试真的会红，再改回来
3. **贴红输出** —— 反向验证时的红输出也要贴进 PROGRESS.md

**为什么**：Superpowers 指出 AI 写测试的最大问题是"**假装失败**"——AI 写完测试直接写实现，跳过真的执行，所以测试可能永远不会失败（或者永远不会真过）。真跑红 = 锁住测试真的能测到东西。

### 影响分析（可选，不卡 ✅）

不是 F1 对账项，不强制。只是 cycle 跑完随手留的**参考笔记**——后续出问题时（CI 挂了、用户反馈异常），可以回到 PROGRESS.md 翻到这条子需求的影响分析，快速定位可能的原因，然后生成真的测试去跑。

- **写在哪**：PROGRESS.md 本子需求证据列**后面**（自由文本，不算 F1 证据）
- **写什么**：可能影响的外部功能 + 可选测试命令
- **不写也能过**：没影响或懒得写 → 跳过，不卡 ✅

### 收点 = F1 事实对账

progress 里写 ✅ 的**那一刻**，F1 触发。cycle 收点的完整 checklist 见 [acr-progress/reference/quality-checklist.md](../acr-progress/reference/quality-checklist.md) §5：
- 验收命令的**原始输出必须在本轮对话内**
- 三天前跑的不算、引用不算、摘要不算
- 没证据 → 不许写 ✅，重跑验证

**cycle 自己不做 F2/F3**——那是 progress 收尾时的事。cycle 只做 F1（收点即触发）。

## cycle 写 PROGRESS.md 什么

cycle **只写两处**：
1. F1 收点时在证据列写命令 + 输出片段
2. 塌方时写需求回写栏

cycle **不碰状态列**（✅/⏳/⬜ 由 progress 根据 cycle 是否完成来写），也**不直接改 prd.md / spec.md**。详细规则见 progress SKILL.md。

## 假设塌方就停

撞见下列任一，停止写码、退回 plan / spec：
- 需修改已确认的接口才能继续
- 出现方案没覆盖的边界
- 同一处反复打补丁
- 实现与 spec 描述的不是一回事

## 快道

plan 判快道后直接进 cycle（不经过 progress，因为状态没变）。cycle 跑完后在 spec §7 快道调整日志里加一条：
```
调整内容 · 实现（改在哪）· 测试验收（怎么证明好了）· 判定依据（对照哪条 Mx.y 验收标准、结论为何）
```

三条规矩：验收栏不许空、判定依据栏不许空、只收快道条目。

## 边界

cycle 只做执行 + TDD + 影响分析 + F1 收点。其他全是其他 skill 的事。
