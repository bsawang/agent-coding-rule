# 技术规格文档

**落点**：`docs/spec.md`（项目级一份），不再分域文件夹。

**输入**：prd.md（设计层业务需求，已审过）。
**输出**：spec 文档 —— Mx.y 子需求编号 + 需求树 + 验收标准 + 设计细化（按档位决定写多少）。

## 编号体系：模块 Mx + 子需求 Mx.y

详细规范见 [reference/numbering.md](reference/numbering.md)。核心要点：
- **两层**：Mx 是模块（brainstorm 切分的业务价值单元），Mx.y 是子需求（spec 分配的可验最小单元）
- **永久锁定**：编号一旦分配，废弃加 🗑，**永不重排、永不删除**
- **ID 不暗示顺序**：依赖关系用 mermaid 需求树画箭头，编号只是引用标签
- **引用格式**：所有文档用 `[M1.2](./spec.md#m12)` 锚点格式

## 三步

1. **写 spec** —— 按 [reference/spec-template.md](reference/spec-template.md) 的结构，只放**结论**。
2. **过合格线** —— 自查题印在模板末尾，逐条过。更完整的 spec 阶段质检见 [acr-progress/reference/quality-checklist.md](../acr-progress/reference/quality-checklist.md) §2。
3. **MX 集合对账（两步，必须都过）** ——
   - ① **模块级**：prd 的 `### Mx` 列表 = spec 的 `### Mx` 列表（grep diff，集合相等）
   - ② **子需求级**：spec 的每个 `#### Mx.y`，其 Mx 必须在 prd 定义过（防止 spec 偷偷加了 prd 没说过的模块）

原始讨论、零散笔记、聊天结论留在会话里或项目特定的笔记里，**不进 acr 文档**。acr 文档只放结论。

## 三层设计合在 spec 里

设计内容不是独立文档，是 spec 的一部分。**写多少由档位决定**：

| 档位 | spec 里写多少设计 | 具体位置 |
|---|---|---|
| 快道 | 不写设计，直接改代码 | — |
| 标准档 | 写**详细设计**（每个子需求下的「详细设计」子节），架构不变 | 每个 Mx.y 的详细设计 |
| 完整档 | 写**架构设计** + 每个模块的**概要** + 每个子需求的**详细设计** | spec 第 3 节架构概览 + 第 4 节每个模块的子节 |

### 架构设计（完整档才写）

回答「**用什么搭**」。落点：spec 第 3 节。

```
3. 架构概览
  3.1 技术底座    语言 / 框架 / 运行时，版本号写死
  3.2 目录与模块边界  代码放哪、边界在哪、什么不许跨
  3.3 存储与通信    数据存哪、模块之间怎么通信
  3.4 部署与运行    怎么起、怎么发
  3.5 约定          命名 / 错误码 / 日志 / 配置 / 测试组织
  3.6 选型记录      每个选型：理由 + 被否决的替代方案
```

**版本号写死**。「Python 3.12」不写「Python 3」。约束不写死，半年后就没人知道当时是按什么写的。

**选型记录**：被否决的替代方案和选中的理由一样重要 —— 否则半年后有人会重新提议同一个方案，再走一遍弯路。只记带锁定的选型（数据库、鉴权方案、部署目标），不是每个库都要记。

### 模块概要（完整档才写）

回答「**分几块、谁的职责**」。落点：spec 第 4 节每个模块开头的子节。

```
4. 功能需求

### M1 本地端采集
  模块概要：
    职责   从 transcript 采集 LLM 调用记录、分类、落库
    输入   transcript 文件 / projects.json 注册表
    输出   SQLite records 表
    依赖   无
    被谁依赖  M2（本地端消费）

  子需求：
    M1.1 ...
    M1.2 ...
```

**按依赖序排列模块**：被依赖者在前。读者从上往下读一遍就能建立完整模型。

### 子需求详细设计（标准档和完整档都写）

回答「**怎么写**」。落点：每个 Mx.y 子节内部。

```
### M1.1 record 采集与去重
  - **验收**：`tokenmetre scan --all` 后 sqlite count 只增不减；重复 scan 条数不变
  - **依赖**：无

  详细设计：
    - 数据流：用户执行 scan → 读 projects.json → 遍历 transcript → ...
    - 字段映射表：ts ← message.timestamp, session_id ← transcript filename, ...
    - UNIQUE 约束：session_id + ts 天然去重
    - derive_category() 判定规则：Bash 首词集 / Write file_exts 优先级 / ...
    - 异常处理：transcript 损坏 → 跳过 + 记 warning
```

详细设计六个固定字段：

```
1 数据流          主流程（文字或 ASCII）
2 接口            签名 / 入参出参 / 错误码 / 幂等性
3 数据结构        字段 + 约束 + 索引
4 算法与规则      关键算法、分类逻辑、公式
5 错误与边界      异常路径 / 并发 / 超时 / 空值 / 越界（每种和正常路径一样详细）
6 测试要点        对应哪些验收标准
```

照着它能写码，不用再回来问。

### 变更传导

| 改了哪层 | 影响 |
|---|---|
| 架构 | 所有模块的概要和所有子需求的详细都要审一遍 |
| 模块概要 | 对应的所有子需求详细要审 |
| 子需求详细 | 只在本层改；若发现概要没覆盖，升级改概要 |

原则：改下层必审上层，改上层必审下游。

## 功能需求的结构秩序（六条硬规矩）

| # | 规矩 | 怎么查 |
|---|---|---|
| 1 | **模块顺序 = 依赖序**，被依赖者在前 | 画依赖图，比对「首次出现位置」是否满足拓扑序 |
| 2 | **需求树 = 依赖图** —— 不显式画 mermaid 就是没完成 | grep `flowchart TD` 或 `flowchart LR` 确认存在 |
| 3 | **同一 Mx.y 在所有文档里呈现一致** | 正则提取各文档的 Mx.y 序列，比集合 |
| 4 | **每个模块/子需求用同一套字段** | 提取每个块的字段名集合，比对是否一致 |
| 5 | **禁止无序罗列** —— 清单必须编号 + 排序依据 | 找没编号的清单；找没写排序依据的编号清单 |
| 6 | **术语首次出现给定义** —— 同一概念不许三个名字 | 挑 3-5 个核心术语，逐个查「首次出现」与「定义」谁在前 |

## 设计词汇

设计「分几块」「接口怎么定」「seam 放哪」时用这套词。用词一致本身就是价值。

- **模块** —— 任何有接口有实现的东西。尺度无关：一个函数、一个类、一个包、一条贯穿多层的切片都算
- **接口** —— 调用方正确使用这个模块所必须知道的一切：类型签名 + 不变量 + 调用顺序约束 + 错误模式 + 需要的配置 + 性能特征
- **实现** —— 模块内部的代码。与**适配器**区分：小适配器可以有大实现（Postgres 仓库），大适配器可以有小实现（内存假件）
- **深度** —— 接口上的杠杆：调用方每学一单位接口能撬动多少行为
- **seam** —— 不修改该处就能改变行为的位置；也就是模块接口所在的那个位置
- **适配器** —— 在某个 seam 上满足某个接口的具体东西
- **杠杆** —— 深度给调用方的好处
- **局部性** —— 深度给维护者的好处：改动、bug、知识、验证都集中在一处

深模块 = 小接口 + 大实现；浅模块 = 大接口 + 小实现（要避免）。

## 硬规矩

- **模块 Mx 和子需求 Mx.y 一旦分配就永久锁定**，废弃标记 🗑，不删除不重排
- **验收标准必须可判** —— 可执行命令或可观察现象。「功能正常」「体验流畅」不合格
- **非目标必须写** —— 明确不做什么，防蔓延
- **待定项带主带期** —— 谁定、何时必须定。无主无期的 TBD 一律当阻塞处理
- **验收条件不许引用未定待定项** —— 待定项关闭前，对应 Mx.y 不得进入 cycle。例：待定项是 CLI 命令名，M2.1 验收里就不能写 `todo add "fix bug"` 这种命令
- **每个子需求的验收 + 详细设计 + 测试要点必须对得上** —— 三者互链

### 详细设计完整度档位门槛

详细设计有六个字段（数据流 / 接口 / 数据结构 / 算法与规则 / 错误与边界 / 测试要点），**不是可选的**。档位决定的是「哪些子需求必须全写」，不是「每个子需求写多少」：

| 档位 | 详细设计完整度要求 |
|---|---|
| 完整档 | **所有** Mx.y 必须六个字段全写 |
| 标准档 | **被改动的** Mx.y 必须六个字段全写；未改动的可只保留验收条件（标注"沿用之前版本"） |
| 快道 | 不触发 spec 重写，直接改代码 + 快道日志 |

## 快道产物：功能实现调整日志

spec 最后一节。**快道 = Mx.y 集合与验收判据都不变** —— 样式布局、实现细节微调，以及 spec 的**表述澄清**都算快道，不新建任何文档，就在日志里追加一条：

```
调整内容（issue / bug / 微调）· 实现（改在哪）· 测试验收（怎么证明好了）· 判定依据（对照了哪条 Mx.y 的验收标准，结论为何）
```

三条规矩：
- **验收栏不许空** —— 空着等于没有证据
- **判定依据栏不许空** —— 写明对照的是哪条 Mx.y 的哪句验收标准、结论是判据未变
- **只收快道条目** —— 标准档与完整档的变更走文档修订与批次，不重复记在这里

## 边界

- 不写新项目脚手架（→ `acr-init`）
- 不写 prd（→ `acr-brainstorm`）
- 不做档位判定（→ `acr-plan` 内置），本 skill 按 plan 判定的档位决定写多少设计
- 不写进度（→ `acr-progress`）
- 不做存量项目审计 / 文档重整（→ `acr-plan` 审计 / rebuild 模式）
