# 开发循环

## 入口：三档判定

档位由**改动落在哪一层文档**决定，不由「改动大小」决定 —— 可判、单调、只能往上升。

本节是**分档的唯一真相源**（`~/.claude/CLAUDE.md` 与各平台 L1 规则只留一行摘要并指向此处，完整定义不重述）。

```
快道     功能点与验收判据都不变    样式布局 · 实现细节微调 · spec 表述澄清
         └ spec 正文可就地改 + 记一条调整日志即完，免设计评审、免循环；
           分主题提交纪律不变

标准档   F 编号集合或验收判据变    在既有模块职责内增改功能点 · 改需求的判法
         概要设计不变
         └ spec 修订 + 详细设计 + 走完整循环

完整档   概要设计 或 架构设计 变    新增模块 · 模块边界变 · 技术底座变
         └ spec → 概要 → 架构 → 详细 + 走完整循环
```

判据落在**语义层**，不落在文件层 —— 判的是「定下来的功能点有没有变」，不是「spec 文件有没有被 edit」。
后者会惩罚文档对齐：改一句话要建循环、过评审、写证据，于是理性选择是不改 spec，文档与实现就此漂移。

**判定句（自检两问）**：

> ① **F 编号集合**要改吗（新增 / 删除功能点）？或任一 F 的**验收判据**要改吗（判什么、怎么判变了）？要改 → 不是快道。
> ② 模块划分要改吗？要改 → 完整档。

**「改表述」与「改判据」的分界**：spec 里句子的**写法**可以变 —— 措辞、背景补充、边界解释、错别字，
只要拿新旧两版对读，**每条验收标准的判据等价**。一旦某条验收标准的判据变了（原来判 A，现在判 B），
就是改需求 → 标准档。

**「补规范空白」怎么算**：原文对某种情况**未作规定**，现在补一条 —— 按这条补充**会不会新增可观察的行为**判：

| 补的是什么 | 档位 | 为什么 |
|---|---|---|
| **新增了可观察的行为**（调用方 / 用户能看到结果不一样） | **标准档** | 「这个功能点做完了没」的判断变了 → 它必须进该 F 的验收标准 |
| **只是澄清**（把已隐含的行为写明白，判据等价） | 快道 | 判据没动，spec 只是更清楚 |

⚠️ **不许用「设计层额外测试、不进 F 的验收标准」这个分类来规避**：**新增了可观察行为就必须进验收标准**。
否则可以把任何新行为都称作"额外保证"，档位就形同虚设 —— 实测踩过这个漏洞。

**升级规则**：任何一档进行中发现上层文档要改，**就地升级、不硬推** —— 快道中 F 集合或验收判据要改 → 升标准档；
标准档中结构要变 → 升完整档。

## 一个完整循环（标准档 / 完整档）

```
④ 设计评审 ★  用户确认门槛
⑤ 进度追加 ★  在 PROGRESS.md 建本次循环
⑥ 实施        按功能点循环
⑦ 测试        全量验证 + 证据留存
⑧ 文档回溯 ★  偏离回填 · 进度收尾 · 验收标准勾对
⑨ 收尾        分主题提交 → 集成决策 → 推送
```

**★ = 硬检查点**：有完成判据，不许跳过。其中要与用户交互的那几关（④、⑨ 的集成决策），
**即使判断"没得选"也必须把判断说出来**再动手 —— 不许静默省略。你判断"只剩一条路"这件事本身要让用户看到，
因为你的判断可能错。

### ④ 设计评审

把方案复述成 3–5 行（含**假设**与**边界**），等用户明确确认。

硬规则「设计未经用户确认，不写任何实现代码」在 `~/.claude/CLAUDE.md`（全局常驻，不在本 skill 重述）。本步做的是**拦截**：

- **Edit / Write 改实现代码一律拦下**，直到用户明确确认。
- 探索性读取、跑命令、写 spec / 文档 / 工单不在拦截范围。
- 用户要求修改 → 退回设计阶段（`acr-brainstorm` / `acr-spec` / `acr-design-docs`）。

**完成判据**：用户明确确认，且确认范围（哪一版方案、确认了哪些假设与边界）有记录。

### ⑤ 进度追加

按 `acr-progress` 在 `PROGRESS.md` 建本次循环：关联 spec 组 + 功能点清单 + 验收标准。

**完成判据**：每个功能点都能在 spec 里找到对应的可判验收标准。找不到 → 退回 `acr-spec` 补。

### ⑥ 实施：功能点循环

一次只推进一个功能点：

```
1 定标准   从 spec 拿验收标准；不可判 → 打回 spec 重写
2 定接口   这个点对外暴露什么 / 依赖什么 / 边界在哪
3 失败测试 先让它红（例外见下）
4 最小实现 只做到让它绿
5 全量验证 不是只跑本点
6 自检+证据 命令 + 原始输出
7 收点     立刻把本点写进 PROGRESS.md（状态 + 证据）→ 下一点
```

四条规矩：**一次一个功能点**；**不攒到最后一起验证**；**每点完成必带证据**；
**收点是原子的** —— 每收一个点**立刻**写 `PROGRESS.md`，不许攒几个点一起改。

> 为什么单列这一条：批量标记会让功能点在两批之间掉落。实测过一次 —— 某功能点的实现与测试
> 都做完了、也口头宣布了 ✅，但那一轮**没发出对应的 Edit**，随后的批量更新又只覆盖了后面几个点，
> 于是它在 `PROGRESS.md` 里**永远停在 ⬜**，而循环已经归档进历史。
> 口头说完成 ≠ 表里改了。判定以表为准。

**第 3 步的例外**：若本功能点的实现已随**前一个**功能点落地（两者共用同一模块），测试会**一到场就是绿的**，
「先让它红」不成立。此时不许沉默跳过，要补一个**替代保证**，两件事都做：

1. **显式声明** —— 说清「本点的判据是事后钉死的、不是驱动实现的」，以及为什么；
2. **反向验证** —— 现场把实现改坏（或临时短路），确认这些测试**真的会红**，再改回来。

「一到场就绿」丢掉了红绿循环的原始保证 —— 测试可能压根没连上实现，或断言写空了恒真。
反向验证把这个保证补回来：**证明这条测试不是恒真**。声明与反向验证的结果一起写进 `PROGRESS.md` 的证据栏。

具体做法见 [reference/tdd.md](reference/tdd.md)（红绿循环、测试放哪、反模式）。

**完成判据**：每个功能点都有本轮的新鲜证据，且本阶段**零未授权 git 动作**。

### ⑦ 测试

任何成功声明（「完成 / 通过 / 修好 / 已解决」）之前，必须有**本轮消息内**跑过的新鲜验证证据。拿不出 → 撤回声明。

> 没在本消息里跑过验证命令，就不许声称通过。

| 借口 | 现实 |
|---|---|
| 「应该能过了」 | 去跑 |
| 「我很确定」 | 确定 ≠ 证据 |
| 「lint 过了」 | lint ≠ 编译 |
| 「只是这一次」 | 没有例外 |

**重构变体**：证据是**行为不变证明** —— 基准全绿，且是同一份基准。

**端到端跑通 / 浏览器级验收**走全局 `verification` 与 `webapp-testing`；本步只管**证据门槛**（本消息内跑过、输出在场）。

**完成判据**：全量验证通过，且输出留在本轮对话里。不过关就不进 ⑧ —— 硬规则「测试不通过不进入收尾」见 `~/.claude/CLAUDE.md`。

### ⑧ 文档回溯

三件事，缺一不可：

1. **偏离回填** —— 实现偏离设计的地方，明确选**改设计文档**还是**改代码**。只有这两个出口，不允许「先这样吧」。
2. **进度收尾** —— 按 `acr-progress` 更新状态与证据。
3. **三方对齐** —— 把 **spec 的 F** ↔ **`PROGRESS.md` 的功能点表** ↔ **实际测试** 逐条对上，三样都要核：

   | 核对 | 查什么 |
   |---|---|
   | spec → 测试 | 每条 F 的验收标准，有没有对应的测试、且通过 |
   | PROGRESS → 测试 | 每个功能点，有没有 ✅ 和证据（命令 + 原始输出） |
   | 条数 | `PROGRESS.md` 的功能点数 = spec 的 F 数 |

   > 只核「spec ↔ 测试」会漏掉一整类错：**实现和测试全对，但 PROGRESS 的表漏改了行**。
   > 实测过一次 —— 勾对脚本核出「spec 点名的 24 个测试全部存在」，但 PROGRESS 里有个功能点
   > 始终停在 ⬜，循环却已归档。那张表是「现在在做什么、剩下什么」的唯一权威源，漏一行就是错的答案。

   能脚本化就脚本化（提取 spec 里点名的测试名、与 `PROGRESS.md` 的功能点表做集合比对），别靠眼看。

另外重跑一遍结构秩序检查（`acr-design-docs` 的七条）—— 文档在循环中被改过，正是顺序最容易乱掉的时刻。

**完成判据**：每条偏离都有出口，每条验收标准都有结论，且三方对齐无缺口。

### ⑨ 收尾

按序执行：

| 步 | 动作 |
|---|---|
| 0 | **评审意见核实** —— 完整读完 → 复述技术要求 → 对照代码核实 → 技术上站得住才实现。禁止「你说得对！」这类附和；任一条不清楚就**全部停下先问**，不许先做清楚的几条 |
| 1 | **文档同步** —— 按仓库文档地图更新。**README 只同步用户侧内容**（什么变了会影响用它的人），开发内容一律进 `docs/`，分工见 `acr-design-docs`；进度表、调整日志按各自 skill |
| 2 | **分主题提交** —— `feat` / `fix` / `docs` 分开，一主题一提交 |
| 3 | **集成决策** —— 直接合 / 开 PR / 保留分支，**给选项让用户选**；若仓库无分支无远端（客观上只剩一条路），**先明说这个判断**再动手，不许静默省略 |
| 4 | **推送** —— 按用户的 git 词执行精确动作序列 |

代码评审的做法见 [reference/review.md](reference/review.md)。

## 边界

- **不自发 git** —— 按个人记忆「开发中不自发 git」执行（真相源在那里，本 skill 不重述）；只读查看（`status` / `diff` / `log`）不受限。
- **假设塌方就停** —— 撞见下列任一，停止写码、退回设计阶段：需修改已确认的接口才能继续 / 出现方案没覆盖的边界 / 同一处反复打补丁 / 实现与 spec 描述的不是一回事。
- 不修 bug 之外的东西（诊断见 [reference/diagnosing.md](reference/diagnosing.md)）。
- 不写需求与设计文档（→ `acr-spec` / `acr-design-docs`）。
- 快道改动不进本流程（→ 直接记 `acr-spec` 第 9 节的调整日志）；快道**允许就地改 spec 的表述**，改动写进日志的「判定依据」栏。
- **从零脚手架新项目**走 `acr-init`；本流程管既有项目的改造与新增。
