# 代码评审

对 `HEAD` 与用户给定的固定点（commit / 分支 / tag / merge-base）之间的 diff 做**双轴评审**：

- **Standards** —— 代码是否符合本仓库已记录的编码规范？
- **Spec** —— 代码是否忠实实现了它来源的需求 / spec？

两轴**并行跑**（各自一个 sub-agent），互不污染 context，最后汇总。

## 步骤

1. **钉住固定点** —— 用户说的那个点。没给就问。记录 diff 命令 `git diff <固定点>...HEAD`（三点，对比 merge-base）与提交列表 `git log <固定点>..HEAD --oneline`。动手前先确认这个引用能解析、diff 非空 —— 坏的引用或空 diff 应该在这里就失败，而不是在两个 sub-agent 里才发现。
2. **找 spec 来源** —— 依次找：提交信息里的 issue 引用；用户给的路径；`docs/` 下匹配分支名或功能名的 spec 文件。都找不到就问用户；确认没有 spec，则 Spec 轴跳过并报「无 spec 可对」。
3. **找规范来源** —— 仓库里任何写明代码该怎么写的文件（`CODING_STANDARDS.md`、`CONTRIBUTING.md` 等）。**仓库规范永远压过下面的味道基线**：仓库认可的做法，基线不再报。
4. **并行起两个 sub-agent** —— Standards 轴把规范来源连同下方的味道基线**全文贴进 prompt**（sub-agent 没有别的渠道拿到它）；Spec 轴贴 diff、提交列表与 spec 全文。两轴都要求：引用原文、区分硬违规与主观判断、工具已强制的跳过、400 字以内。
5. **汇总** —— 分 `## Standards` 与 `## Spec` 两节并列呈现，**不合并、不重排**。结尾一行总结：各轴发现总数、各轴最严重的一条。**不要跨轴挑一个总冠军** —— 分开呈现正是为了阻止这种重排。

## 为什么分两轴

一个改动可能过一轴挂另一轴：符合所有规范但做错了事 → Standards 过、Spec 挂；完全按需求做但破坏项目惯例 → Spec 过、Standards 挂。分开报，一轴才不会掩盖另一轴。

## 味道基线（仓库没写规范时也适用）

每条都是**标注过的启发式**（「疑似 Feature Envy」），不是硬违规；工具已强制的跳过。

- **神秘命名** —— 名字没揭示它做什么或装什么。→ 改名；想不出诚实的名字，说明设计本身含混。
- **重复代码** —— 同一逻辑形状出现在不止一处。→ 抽出共享形状，两边都调它。
- **依恋情结** —— 一个方法访问别的对象的数据比自己的还多。→ 把方法搬到它依恋的数据上。
- **数据泥团** —— 同几个字段或参数总是一起出现（一个正在孕育的类型）。→ 打包成一个类型传。
- **基本类型偏执** —— 用基本类型或字符串顶替一个本该有自己的类型的概念。→ 给这个概念一个小类型。
- **重复的 switch** —— 同一个 switch / if 级联反复出现。→ 换成多态，或两处共用一张映射表。
- **霰弹式修改** —— 一个逻辑改动逼迫大量文件散点式修改。→ 把一起变的东西收到一个模块里。
- **发散式变化** —— 一个文件因几种互不相关的原因被改。→ 拆开，让每个模块只为一个原因而变。
- **夸夸其谈通用性** —— 加上了 spec 并没有需要的抽象、参数、钩子。→ 删掉，先内联回去，等真实需求出现。
- **过长的消息链** —— `a.b().c().d()` 这种调用方不该依赖的导航。→ 在第一个对象上用一个方法把整条路藏起来。
- **中间人** —— 一个类或函数大部分只是往下转发。→ 砍掉，直接调真正的目标。
- **被拒绝的遗赠** —— 子类忽略或覆盖掉了它继承的大部分东西。→ 放弃继承，改用组合。
