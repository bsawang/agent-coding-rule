# 开发进度

**落点**：`PROGRESS.md`，项目根或 `docs/`，**全项目一份**。

进度文档是「现在在做什么、剩下什么」的单点答案。分散成多份就要翻好几处才知道全局，那就失去了它的意义。

## 结构

```
{项目名} 开发进度

  当前：循环 2 {spec-003, spec-004}  ⏳ 进行中
    范围      覆盖 spec-003 全文 + spec-004 第 4 节
    功能点    F1 ✅（证据：pytest 全绿 + 原始输出）
              F2 ⏳（阻塞：等接口确认）
              F3 ⬜
    偏离      详细设计说用队列，实现改了轮询 → 已回填 spec-003 详细设计 §4
    待定      错误码命名待定（决策人：我 / 期限：本循环结束前）

  历史：循环 1 {spec-001, spec-002}  ✅ 2026-09-14
```

## 什么时候写

| 时机 | 动作 |
|---|---|
| 循环开始（`acr-cycle` ⑤） | 新建一节，登记范围、功能点清单、验收标准 |
| 每个功能点完成 | **当场**状态改 ✅，**附证据**（命令 + 原始输出）—— 不攒几个点一起改 |
| 出现阻塞 | 功能点标 ⏳，写明阻塞在等什么 |
| 发现有偏离 | 记一笔，并写明出口（改设计文档 / 改代码） |
| 循环结束（⑧） | 状态收尾、待定项清账、循环移入历史 |

## 硬规矩

- **每个 ✅ 后面必须有证据** —— 命令 + 原始输出。没有证据的 ✅ 是假的完成。
- **收点即写，不许批量** —— 功能点一完成就立刻改这张表。攒几个点一起改会让行在两批之间掉落：
  实测过一次，某功能点实现与测试都做完、也口头宣布了 ✅，但那一轮没改表，随后的批量更新又只覆盖了
  后面几个点，于是它**永远停在 ⬜**，而循环已归档。**判定以表为准，口头说完成不算。**
- **每条偏离必须指定出口** —— 改设计文档或改代码，二选一。不允许「先这样吧」。
- **待定项带主带期** —— 谁定、何时必须定。循环收尾时逐条清账，逾期的当阻塞处理。
- **以循环为单位** —— 一行一个循环，不是一个 spec 一行。
- **只记状态，不记过程** —— 讨论、试错、走过的弯路属于 `<slug>.discussion.md` 或会话记录。进度文档是给「快速看清现状」用的，塞满过程就没人看了。

## 边界

- 不写需求与设计内容（→ `acr-spec` / `acr-design-docs`），只引用编号与路径。
- 不管流程怎么走（→ `acr-cycle`）：本 skill 只负责把流程产生的状态如实记下来。
