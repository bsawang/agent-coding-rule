# 设计文档

**输入**：已确认的需求文档（spec）。
**输出**：按档位产出概要设计 / 架构设计 / 详细设计，或改写根目录 README。

## 三层各答什么

| 层 | 答 | 不答 | 归属 |
|---|---|---|---|
| 概要设计 `<slug>.hld.md` | **分几块** · 谁的职责 · 谁依赖谁 | 技术选型 · 字段级细节 | 每个需求域 |
| 架构设计 `ARCHITECTURE.md` | **用什么搭** · 代码放哪 · 怎么起 | 单个功能的内部流程 | 项目级，一份，增量修订 |
| 详细设计 `<slug>.lld.md` | **怎么写** · 签名 / 字段 / 错误 / 边界 | 系统级结构 | 每个需求域 |

模板：[reference/hld.md](reference/hld.md) · [reference/architecture.md](reference/architecture.md) · [reference/lld.md](reference/lld.md)
设计模块接口时用的词汇（接口、深度、seam 的判据）：[reference/design-vocab.md](reference/design-vocab.md)

**功能点编号贯穿全链** —— spec 里定的 `F1…Fn`，三层设计文档、进度文档、测试用例都用同一套编号，任何一份文档都能反查到功能点。

## 结构秩序（七条硬规矩）

1. **章节顺序 = 模板顺序**，不跳号、不插队、不凭空多出「补充说明」一节。
2. **同一编号同一顺序** —— `F1…Fn` 在五份文档里呈现顺序一致。
3. **阅读顺序 = 依赖顺序** —— 被依赖者先出现；讲 A 时不许引用还没介绍的 B。
4. **描述结构统一** —— 每个模块/功能点用同一套字段：职责 → 输入 → 输出 → 依赖。
5. **禁止无序罗列** —— 清单必须编号，且写明排序依据（依赖序 / 执行序）。
6. **术语首次出现给定义** —— 同一概念不许在三处叫三个名字。
7. **层级递进** —— 详细设计不出现概要设计没提过的模块；详细不重述概要已说的结构。

## README 与 docs 的分工

| 文档 | 写给谁 | 放什么 | 不放什么 |
|---|---|---|---|
| 根目录 `README.md` | **用户侧** —— 要用它的人 | 这是什么 · 怎么装/启用 · 怎么用 · 能力清单 · 去哪看更多 | **一切开发内容**：设计决策、模块划分、演进史、待定项、进度、实现细节 |
| `docs/` | **开发侧** —— 改它的人 | 需求 / 概要 / 架构 / 详细设计、进度、缺陷文档 | 使用说明 |

判据一句话：**这段内容是给「要用它的人」看，还是给「改它的人」看？**

## 三条通用红线（任一层都适用）

| 红线 | 样子 | 处置 |
|---|---|---|
| 只有描述，没有决策 | 「模块会处理用户数据」 | 打回，改成「谁、在什么时候、怎么处理」 |
| 只有结论，没有理由 | 「用 Redis 做缓存」 | 补理由 + 被否决的替代方案 |
| TBD 无主无期 | 「错误码待定」 | 补决策人 + 期限，逾期当阻塞 |

## 修订触发

架构设计一旦触及下列任一，**必须回改 `ARCHITECTURE.md`**：换依赖 / 改目录结构 / 改通信方式 / 改错误码约定。改完在循环的 ⑧ 文档回溯里记一笔。

## 边界

- 不写需求文档（→ `acr-spec`）。
- 不改存量项目的既有文档（→ `acr-retrofit`，且原文档一律不动）。
- 不写实现代码（→ `acr-cycle`）。
