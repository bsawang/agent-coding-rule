# 代码层编码规范

**SSOT 声明**：本文件是 acr 流程对**项目代码层硬约束的唯一真相源**——模块边界、错误处理、测试组织、TDD、依赖管理全在这。其他 skill 只引用，不重复写。全局真相源体系（六层六源 + 禁止事项 + 镜像同步）见 `docs/SSOT.md`。

**项目特定规范**（命名 / 目录结构 / 错误码格式 / 日志风格 / 配置方式）不在本文件里——由 spec §3.2 目录与模块边界 + §3.5 约定 定义，本文件只写**跨技术栈通用的硬约束**。

---

## 1. 模块边界（硬约束，不许违反）

**真相源**：spec §3.2 目录与模块边界。

spec 写架构时必须明确：
- 目录里每个文件的职责（一句话）
- **import 边界**：哪些模块不许互相 import

cycle 执行时**不许跨边界 import**。发现需要跨边界 → 说明 spec 的模块划分有问题 → 先停，走 plan 重新判定（可能升级为完整档）。

| 常见边界反模式 | 正确做法 |
|---|---|
| cli 直接操作 DB | cli → core → db（cli 只做参数解析 + 输出） |
| db 层包含业务逻辑 | db 只管连接 + schema + 原始 SQL，业务在 core |
| core 直接依赖 HTTP 框架 | core 返回 dict/对象，HTTP 层做序列化 |
| 测试里 import 生产代码的私有函数 | 测试通过公开接口测；私有函数拆成模块级函数再测 |

## 2. 错误处理（硬约束）

每个 Mx.y 的 spec 详细设计里必须有**「错误与边界」**字段，列出：
- 所有可能的错误场景（输入非法 / 资源不存在 / 外部依赖失败 / 并发冲突）
- 每种错误的返回值（异常类型 / 错误码 / HTTP status）
- 每种错误对用户的提示（人类可读）

cycle 实现时**必须覆盖所有列出的错误场景**——少一个就是没实现完。

**禁止**：`except Exception: pass` / 错误返回空值不说明原因 / 把技术异常直接抛给用户（如 SQL 语法错误）。

## 3. 测试组织（硬约束）

**一个 Mx.y = 一组验收测试**。测试文件 / 测试类命名必须能映射回 Mx.y：

```python
# spec M1.2 短码生成算法 → 测试文件
# test_shorten.py::test_code_generation
def test_code_generation():
    ...
```

TDD 硬约束（cycle 第③步）：
1. 先写测试（按 spec 验收条件）
2. **真跑一遍确认红**（pytest 必须有 FAILED 输出）
3. 贴红输出到 PROGRESS.md 证据列
4. 写最小实现 → 绿 → 自检验收全过

**禁止**：测试一上来就是绿的（反向验证必须真看到红）；测试用代码自己算期望值（同义反复）。

## 4. 依赖管理（硬约束）

- **不许引入 spec 未声明的依赖**（spec §3.1 技术底座）。需要新依赖 → 先改 spec → plan 重新判定档位
- 新增依赖必须说明理由（在 spec §3.1 加一行：为什么需要 + 有什么替代方案被否决）
- 锁定版本号（spec §3.1 里写精确版本，不写 `^1.0` 或 `>=1.0`）

## 5. 单一职责（硬约束）

**一个模块 = spec §3.2 定义的一个职责**。出现以下情况说明模块划分错了：
- 一个 500+ 行的文件干三件事（解析 + 业务 + 存储）
- 一个函数名里有 "and" / "同时"
- 改一个功能要同时改三个不相关的类

发现上帝类 → 先停，走 plan 重判（可能升级为完整档改模块划分）。

## 6. 快道改动的代码约束

快道 = Mx.y 集合不变 + 验收判据不变。但快道改动**必须**：
- 有测试覆盖（在 spec §7 快道日志里写清楚"改了哪 + 什么测试证明没坏"）
- 不引入新依赖
- 不跨模块边界

快道日志格式（spec 最后一节）：

| 日期 | 调整内容 | 实现（改在哪） | 测试验收 | 判定依据 |
|---|---|---|---|---|
| 2026-09-18 | 修复短码冲突概率计算 | `src/core.py::generate_code()` | `pytest tests/test_shorten.py::test_collision_prob → 3 passed` | M1.2 验收条件"冲突率 < 0.01%"未变，只是实现从 naive 换成 hash |
