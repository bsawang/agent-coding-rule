# 缺陷文档模板

落点：`docs-rebuilt/GAPS.md`

这是重整评审的产物，也是用户后续补充的**工作清单**。补一条勾一条。

## 四类问题

| 类型 | 意思 |
|---|---|
| **缺失** | 该有的内容没有 |
| **含糊** | 写了，但不可判 —— 读者据此做不了决定 |
| **矛盾** | 两处说法打架 |
| **未确认** | 从上下文或代码推断出来的，代码里证实不了 |

**未确认**这一类是防「编造设计」的闸门。凡是推断出来的意图，一律先记在这里，用户确认后才进正文。宁可缺，不可编。

## 结构

```
| # | 位置            | 类型   | 问题                            | 需你补充          | 状态 |
| 1 | 概要设计 §2     | 缺失   | 订单模块的职责边界没写           | 该模块管到哪一步   | ⬜ |
| 2 | 详细设计 §4     | 含糊   | "异步处理返回值" —— 返回什么     | 明确返回结构      | ⬜ |
| 3 | 架构设计 §1     | 矛盾   | 一处写 SQLite，一处写 Postgres   | 定一个            | ⬜ |
| 4 | 概要设计 §3     | 未确认 | 推断的重试机制，代码里找不到依据  | 是否真有此设计     | ⬜ |
| 5 | 无归属          | ——     | 旧文档「临时说明」一节无对应章节  | 归到哪一节，或废弃 | ⬜ |
```

**位置**列写清哪份文档哪一节；**无归属**用于映射表里找不到落点的旧内容 —— 这类内容不许直接丢，先挂在这里。

## 写作要点

**问题写具体的**：「这段说不清」不合格；「返回什么结构没说」才行。用户看清单时不该再回来问你什么意思。

**需你补充写可执行的**：用户要做什么才能勾掉这一条。「补充文档」不合格；「明确该模块管到哪一步、到哪一步交给支付模块」才行。

**一条一个位置**：一条覆盖多个位置的，拆成多条。清单的价值就在能逐条勾。

## 勾对时的检查

- [ ] 每条都定位到具体文档的具体章节了吗？
- [ ] 「未确认」类的条目，用户确认后才移进正文了吗？
- [ ] 映射不上的旧内容，都在「无归属」里有记录吗？
- [ ] 用户补完后，正文更新了、状态也勾了吗（不许只勾不改）？
