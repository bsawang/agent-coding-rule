# 需求文档

**输入**：讨论清楚的（或需要落清的）需求。
**输出**：`docs/specs/<domain>/<slug>.spec.md`。

## 三步

1. **分流讨论记录** —— 原始讨论、零散笔记、聊天里的结论，全部进 `<slug>.discussion.md`。这是**倾倒口**：讨论可以详尽、可以乱。
2. **写 spec** —— 只放**结论**，按 [reference/spec-template.md](reference/spec-template.md) 的九节结构；讨论记录在正文只留索引。
3. **过合格线** —— 自查题印在模板末尾，逐条过。

## 硬规矩

- **功能点编号 `F1…Fn`** —— 按依赖/执行顺序编号，不按想到的顺序。这套编号贯穿 spec / 概要 / 详细 / 进度 / 调整日志五份文档，呈现顺序必须一致（见 `acr-design-docs` 的结构秩序）。
- **验收标准必须可判** —— 可执行命令或可观察现象。「功能正常」「体验流畅」不合格，打回重写。
- **非目标必须写** —— 明确不做什么，防蔓延。写不出非目标，说明范围还没想清。
- **待定项带主带期** —— 谁定、何时必须定。无主无期的 TBD 一律当阻塞处理。

## 快道产物：功能实现调整日志

spec 第 9 节。不改变 spec 的改动（样式布局、实现细节微调）不新建任何文档，就在日志里追加一条：

```
调整内容（issue / bug / 微调）· 实现（改在哪）· 测试验收（怎么证明好了）
```

**验收栏不许空** —— 空着等于没有证据。这条规矩把「证据先于断言」落到了最小改动上。

只收快道条目。标准档（spec 变）与完整档（概要或架构变）的变更走文档修订与循环，不重复记在这里，否则会造第二真相源。

## 边界

- 不写概要/架构/详细设计（→ `acr-design-docs`）。
- 不写进度（→ `acr-progress`）。
- 档位判定是 `acr-cycle` 的入口动作，本 skill 按判定结果执行，不自己判。
- **共创式文档讨论**（多轮打磨 proposal / 技术文档）走全局 `doc-coauthoring`；本 skill 按模板把已定的结论落成需求文档。
