# 需求文档模板

落点：`docs/specs/<domain>/<slug>.spec.md`

## 结构

```
0 元信息       状态（草稿 / 已确认）· 日期 · 决策人
1 背景与问题   现象 + 代价 —— 为什么现在做
2 目标 / 非目标  非目标必须写，明确不做什么
3 用户场景     谁 · 什么情况下用 · 现在怎么凑合
4 功能点       F1…Fn，每条 = 一句话描述 + 验收标准
5 边界与异常   含「明确不处理」的
6 影响面       接口 / 数据 / 依赖 / 兼容性 / 迁移
7 待定项       开放问题 + 谁来定 + 何时必须定
8 讨论记录     时间线索引（正文指回 <slug>.discussion.md）
9 功能实现调整日志  快道变更挂这里（含 spec 表述澄清）
```

## 写作要点

**第 1 节 背景与问题**：写现象与代价，不写解决方案。「上传大文件时用户反复点击，导致重复提交」是现象；「要加防重复提交」是方案，属于第 4 节。

**第 4 节 功能点**：每条独立可验。编号按依赖/执行顺序 —— 前置功能点编号小。

```
F1 用户可以上传 5GB 以内的文件
   验收：`uv run pytest tests/test_upload.py -k large` 通过
        且 5GB 文件上传后 `ls uploads/` 可见完整文件

F2 上传中断后可以续传
   验收：`bash scripts/test_resume.sh` 输出 `resumed from 2.1GB`
```

验收标准**写成可执行的**：一条命令、一段脚本、一个可观察现象。写不出可执行的，说明功能点还没想清。

**第 5 节 边界与异常**：「明确不处理」和「要处理」一样重要 —— 前者防止范围蔓延，后者防止漏测。

**第 7 节 待定项**：

```
| # | 待定 | 谁来定 | 何时必须定 |
| 1 | 错误码命名规则 | 我 | 本循环结束前 |
```

## 合格线（写完逐条过）

- [ ] 非目标写了吗？写得出「这次不做什么」吗？
- [ ] 每条功能点的验收标准可判吗 —— 是可执行命令或可观察现象，而不是形容词？
- [ ] 第 6 节影响面列全了吗 —— 接口、数据、依赖、兼容性、迁移，触及的都要写？
- [ ] 每条待定项都有主有期吗？
- [ ] 第 9 节（若有条目）每条的**验收栏**与**判定依据栏**都不空吗 —— 判定依据写的是对照了哪条 F 的验收标准？
      改了 spec 正文的，写明改在哪一节了吗？
- [ ] 通读一遍：需要跳读才能理解吗？F 编号顺序是依赖顺序吗？
