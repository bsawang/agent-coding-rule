# 红绿循环

功能点循环里 ③ 失败测试 → ④ 最小实现 的做法参考。

## 什么是好测试

测试通过**公开接口**验证行为，不碰实现细节。代码可以整个换掉，测试不该跟着变。好测试读起来像一句规格说明 —— 「带有效购物车的用户可以结账」直接告诉你有什么能力 —— 而且能扛住重构，因为它不关心内部结构。

## seam —— 测试写在哪

**seam** 是你测试所在的公开边界：从那里观察行为，而不用伸手进去。测试写在 seam 上，绝不针对内部。

**只在事先约定的 seam 上写测试。** 写任何测试之前，先把要测的 seam 列出来与用户确认；未确认的 seam 不写测试。测不完所有东西 —— 事先约定 seam，正是让测试精力落在关键路径与复杂逻辑上，而不是每个边界情况上的办法。

先问：公开接口是什么？要测哪几个 seam？

接口形状本身存疑时（模块该多深、seam 该放哪、接口该暴露什么），查 `acr-design-docs` 的 [design-vocab.md](../../acr-design-docs/reference/design-vocab.md)。

## 三个反模式

- **实现耦合** —— mock 内部协作者、测私有方法、从侧门（直接查数据库而不是走接口）验证。识别信号：重构时测试红了，但行为没变。
- **同义反复** —— 断言用代码算期望值的方式算出来（`expect(add(a, b)).toBe(a + b)`、手工按同样方式推出的快照、常量断言等于自己），于是它按构造必然通过，永远不可能和代码意见不合。期望值必须来自独立的真相源：已知正确的字面量、算好的样例、spec。
- **水平切片** —— 先把测试全写完再写实现。批量写测试验证的是**想象中**的行为：测的是东西的**形状**而不是面向用户的行为，测试对真正变化失去敏感，而且在还没理解实现前就锁死了测试结构。改成**垂直切片**：一个测试 → 一个实现 → 再来一个，每个测试都是**曳光弹**，根据上一轮学到的东西调整。

## 循环规则

- **红在绿前** —— 先写会失败的测试，再写刚好让它过的代码。不预先替后面的测试写代码，不加投机性功能。
- **一次一个切片** —— 一个 seam、一个测试、一个最小实现为一轮。
- **重构不属于这个循环** —— 重构属于评审阶段，不属于红绿循环。
