# 架构设计模板

落点：`ARCHITECTURE.md`（项目根或 `docs/`），**项目级一份**，建一次之后增量修订。

回答的是「**用什么搭**」。单个功能的内部流程不属于这里。

## 结构

```
1 技术底座      语言 / 框架 / 运行时，版本号写死
2 目录与模块边界 代码放哪、边界在哪、什么不许跨
3 存储与通信    数据存哪、模块之间怎么通信
4 部署与运行    怎么起、怎么发
5 约定          命名 / 错误码 / 日志 / 配置 / 测试组织
6 选型记录      每个选型：理由 + 被否决的替代方案
```

## 写作要点

**版本号写死**。「Python 3.12」不写「Python 3」；「Postgres 16」不写「Postgres」。约束不写死，半年后就没人知道当时是按什么写的。

**第 6 节 选型记录** —— 每条格式：

```
选 Postgres 做写模型
  理由     需要事务与唯一约束，数据量在单机可承受范围
  否决     SQLite（并发写不够）、MongoDB（事务不满足）
```

被否决的替代方案和选中的理由一样重要 —— 否则半年后有人会重新提议同一个方案，再走一遍弯路。

**只记带锁定的选型**：数据库、消息总线、鉴权方案、部署目标。不是每个库都要记；判断标准是「换掉它要花一个季度吗」。

## 合格线（写完逐条过）

- [ ] 每个选型都带理由 + 被否决的替代方案吗？
- [ ] 版本号写死了吗？
- [ ] 新人能靠第 2 节知道「这段代码该放哪个目录」吗？
- [ ] 有没有写进单个功能的内部流程（那属于详细设计）？
- [ ] 第 5 节的约定，是不是都是代码里看不出来、只能靠文档传的？（能靠配置/脚本看出来的别抄进来）
